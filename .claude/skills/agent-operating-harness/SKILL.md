# Agent Operating Harness

## Purpose
Compose the repository research skills into one bounded, repeatable operating
harness for autonomous diligence and architecture analysis.

## When to Use
- Running a full-repository diligence pass
- Coordinating multiple independent evidence threads
- Turning research into a reusable agent execution blueprint
- Governing what can be claimed complete or verified

## Required Evidence
- Default to zero mock data and zero fabricated fallbacks
- Require first-hand verification before success claims
- Fail closed when required evidence is missing or weak
- Maintain one canonical issue/PR linkage for implementation work
- Do not introduce alternate product or storage truth unless the repository
  explicitly authorizes it
- Keep concurrency limited to independent evidence threads only

## Execution Order
1. `canonical-architecture-truth`
2. `persistence-and-boundary-truth`
3. `engineering-risk-and-duplication-audit`
4. `github-ops-and-workflow-health`
5. `product-positioning-and-buyer-fit`

## Outputs
- Canonical-vs-legacy map
- Persistence truth map
- Security boundary map
- Risk register
- Workflow health report
- Product-fit memo
- Remediation sequence with verification gates
