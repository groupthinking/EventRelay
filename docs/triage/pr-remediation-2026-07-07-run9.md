## Actionable finding: `#588` breaks `main` if merged

`#588` ("Upgrade `@sentry/nextjs` dependency target for Next.js 16 compatibility",
Copilot) bumped `apps/web/package.json` from `@sentry/nextjs@^10.63.0` to `^11.0.0`.

**There is no v11.** npm `latest` is `10.63.0`:

```
$ npm view @sentry/nextjs dist-tags
{ v7: '7.120.4', v8: '8.55.2', v9: '9.47.1', latest: '10.63.0', next: '10.50.0-alpha.0' }
```

Every dep-installing CI job on `#588` failed at the install step (not build):

```
npm error code ETARGET
npm error notarget No matching version found for @sentry/nextjs@^11.0.0.
```

→ `build`, `lint-frontend`, `npm-audit` all red; `mergeable_state: blocked`. Merging it
would break `npm install` on `main`.

**The PR is also unnecessary.** The original `next build` config-load failure it targeted
(`@sentry/nextjs` failing to resolve `@opentelemetry/*` at import time) is already fixed
on current `main`: the last completed `main` CI runs (`f5a5dcb`, `adec5eb3`) are green
with `@sentry/nextjs@^10.63.0` and the existing unconditional
`require('@sentry/nextjs')` in `apps/web/next.config.js`. Reverting the bump to
`^10.63.0` would make `#588` a no-op against `main`; there is no version to bump *to*.

**Action taken:** posted the root-cause diagnosis on `#588` and **closed it** as
superseded/invalid. If additional config-load hardening is wanted, `#570`'s
guarded-`require` fallback (still draft) is the correct approach and does not touch the
dependency version — that remains an owner decision.
